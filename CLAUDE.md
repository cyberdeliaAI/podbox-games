# PodBox games

Games for the Arcade of [PodBox](https://github.com/anthonyfletcher/podbox), a Rockbox-based firmware for the iPod Video and iPod Classic. Each game is a cart: a folder of `.js` files in a small JavaScript subset plus art, sounds and data, compiled into a `.pbg` the iPod plays.

| Cart | Folder | What it is | Doc |
|---|---|---|---|
| Pulse Tunnel | `pulsetunnel/` | 3D tube shooter that flies to the owner's music | `docs/pulsetunnel.md` |
| Marble Chain | `marbles/` | Marble shooter: six levels, three tracks, power-ups | `docs/marbles.md` |

The repo is private. The owner works in English: code, comments, docs and commit messages.

## Layout

```

  levels.js                   the six levels, the three tracks, saved progress
  title.js                    start screen, level picker, how to play
  data/path1-3.json           tracks: one point a pixel, plus a 20x15 reach map
  images/bg1-3.png, sheet.png, logo.png    generated by tools/marbles_assets.py
  sounds/*.json               sfxr settings
pulsetunnel/                  Pulse Tunnel
  cart.json                   music: control, suspend: false, three options
  main.js                     clock, tempo, beat grid, planning, ship, run, screens
  tube.js                     projection, rings, spokes, palette from album colours
  foes.js                     enemies, gates, pickups, sparks
  shots.js                    the auto-firing guns
  hud.js                      score, shields, bombs, messages, title, game over
  logo.png, sounds/*.json
tools/
  marbles_assets.py           Marble Chain tracks, backgrounds, sprite sheet, logo
  marbles_stress.py           Marble Chain stress test: autoplay, invariant checks, units a tick
  marbles_stress.js           the in-cart half of it, copied into a scratch build as stress.js
  pulsetunnel_logo.py         Pulse Tunnel logo
```

## Setup

The SDK lives in the PodBox repo, cloned next to this one:

```sh
git clone https://github.com/anthonyfletcher/podbox ../podbox     # --depth 1 is enough
(cd ../podbox/arcade/sdk && npm ci --omit=dev)                     # once; needs Node 20+
(cd ../podbox/arcade/sdk && sh host/build.sh)                      # once; builds host/pbgvm and host/pbgide
```

Python 3 with Pillow is needed for `tools/`.

## Build

```sh
sh build.sh                              # every cart into dist/
SDK=/path/to/arcade/sdk sh build.sh      # SDK somewhere else
node ../podbox/arcade/sdk/pbgc.js build marbles -o dist/marbles.pbg    # one cart
node ../podbox/arcade/sdk/pbgc.js dis dist/marbles.pbg                 # check it, list bytecode
```

A clean build prints one line a cart (size, functions, globals). Compile errors name the file, line and column. CI builds with `anthonyfletcher/podbox-arcade-builder@latest`, not with `../podbox`, so the two can drift apart when the SDK changes.

A `.pbg` carries its own sources: `pbgc unpack` gives every file back. Anyone holding a built cart can read the code.

## Run, test and measure

Everything is checked by running the cart headless in `pbgvm`, the iPod's engine built for this machine.

### Marble Chain stress test

Run it after any change to `marbles/`, and always after touching `chain.js`, `gun.js` or the drive logic in `main.js`:

```sh
python3 tools/marbles_stress.py                       # levels 1-6, seeds 1 and 2, smart and blind, 9,000 ticks: about a second
python3 tools/marbles_stress.py --levels 6 --modes smart,blind,still --seeds 1,2,3 --ticks 20000
python3 tools/marbles_stress.py --selftest            # POP raised to 12 in a scratch copy: the checks must fail
```

- It copies `marbles/` to a temp folder, adds `tools/marbles_stress.js` as `stress.js`, inserts `stress.tick();` after `function update() {` in `main.js`, builds the copy and runs `pbgvm`. The cart's own files are never touched. If that line changes, the tool stops and says so.
- `stress.tick()` checks the nine invariants below, then plays: it starts the level, shoots every `--every` ticks (default 20, 0.6 s) and restarts after a win or a loss. Settings reach it through `pbgvm --setting` and `sys.setting()`.
- Modes: `smart` aims where the loaded ball pops a run, nearest the hole, and swaps when the next ball does better (about 50% of its shots pop). `blind` shoots at random. `still` never shoots.
- Units are per tick of play, with the harness's own `prof("stress_*")` sections subtracted. Columns: shots, hit% (shots whose own landing popped), won, lost, max combo, max balls, power-ups seen, avg, p95, p99, max, and the share of ticks over 12,500 and 17,500.
- Exit status 1 on any invariant violation or runtime error. Warnings (`recycle`: a popping or arriving ball about to be sent back to the tunnel by `rewind()`) are reported but don't fail the run.
- `--keep` keeps the scratch build, `--verbose` prints every problem line, `--jobs` sets how many runs go at once.
- The harness's globals live in the `stress` namespace, so they can't clash with `main.js`, but they still can't take API names (`target` is one).

### Running a cart by hand

```sh
VM=../podbox/arcade/sdk/host/pbgvm
$VM dist/marbles.pbg --ticks 600 --units --seed 1          # units per tick go to stderr
$VM dist/marbles.pbg --ticks 600 --shot out.png            # 320x240 screenshot after the last tick
$VM dist/pulsetunnel.pbg --ticks 900 --playing --beat 128 --buttons 70:16,71:0 --units
```

- `--units` prints `start N` then `tick T N` for each tick, on stderr. `printh()` goes to stdout. A runtime error goes to stderr and exits 1.
- `--seed s` makes a run repeatable.
- `--buttons t:mask,...` holds a button mask from tick t until the next entry: 1 Prev, 2 Next, 4 Menu, 8 Play, 16 Select. A tap of Select is `t:16,t+1:0`.
- `--wheel t:clicks:pos` turns the wheel at tick t and puts the finger at pos (0 to 95 clockwise from the top, -1 lifts it). `t:0:pos` just moves the thumb, which is how Thumb aiming is driven.
- `--playing --beat bpm` fakes music at a steady tempo. Pulse Tunnel needs this to exercise the beat code.
- `--saves file` keeps `dset()` numbers between runs. The file is 256 little-endian int32s then 32 bytes of fraction bits. To start Marble Chain with all six levels open: `python3 -c "import struct; open('s.bin','wb').write(struct.pack('<256i', 6, *[0]*255) + bytes(32))"` then `--saves s.bin` and press Select at tick 20 (Play continues at level 6).
- `prof("name")` ... `prof()` in code prints `prof name units` with `--units`. Use it to time a section; it costs nothing on the iPod.
- `--memory`, `--dirty`, `--skip t:n` (a late, undrawn tick) and the rest are listed at the top of `../podbox/arcade/sdk/host/pbgvm.c`.

Pulse Tunnel has `const AUTOPILOT = false;` in `main.js`. Set it to `true` in a scratch copy for long unattended runs. Marble Chain's autoplay is the stress test above.

The IDE (`../podbox/arcade/sdk/host/pbgide marbles`) edits a cart folder in place and has a profiler, replays and Run as iPod Video playing FLAC.

## The performance budget

Performance is the hard constraint. Every change that adds work per tick gets measured with `pbgvm --units` before it's called done.

| Rate | Units a tick, iPod Video playing FLAC, full redraw |
|---|---|
| 33 (both carts' default) | about 12,500 |
| 25 (the fallback) | about 17,500 |

- A unit is about 1.9 µs on that iPod. The iPod Classic has about 175,000 a tick, so the Video is the only target that matters.
- Aim well under the budget. Look at p95 and the max, not just the average.
- Rough costs: a script step 2 to 4, a loop turn 4, a function call about 3, `sprites.draw` about 35 a sprite, `spr` in a loop about 70, `rspr` about 320 for an 8x8 sprite and 790 for 16x16 (measured; avoid it), a string join 24, `cls` 200, a whole-screen `blit` 6,000 (1,000 with `palt(0, false)`), a FONT.CAPS character 12, `color.toned` 950, `beat.listen(true)` 6,300 a tick while listening.
- Prefer the engine's systems (`sprites.draw`, `particles`) over script loops. Keep hot arrays global. Allocate nothing in `update()` and `draw()`: garbage collection costs time the units don't show.
- Both carts watch `skipped()` and call `setrate(25)` after more than 4 late frames in a second. Speeds are scaled by `33.0 / rate()` (Marble Chain) or run on music milliseconds (Pulse Tunnel), so the game plays the same at 25.
- Full model and formula: `../podbox/arcade/manual/reference-fast.md`.

Baseline measured 2026-11-14 with SDK `126ebba`, units a tick of play. Marble Chain rows come from `tools/marbles_stress.py` (two seeds, 9,000 ticks, a shot every 20 ticks; still is seed 1):

| Run | Avg | p95 | Max | Over 12,500 |
|---|---|---|---|---|
| Marble Chain, start screen (pbgvm, no input) | 3,850 | 5,500 | 5,560 | 0% |
| Marble Chain, smart, level 1 | 4,750 | 7,050 | 8,900 | 0% |
| Marble Chain, smart, level 6 | 6,200 | 8,800 | 11,850 | 0% |
| Marble Chain, smart, all levels | 5,280 | 7,930 | 11,850 | 0% |
| Marble Chain, still, level 6 | 11,200 | 16,400 | 17,800 | 36% |
| Marble Chain, blind, level 3 | 10,600 | 16,700 | 22,800 | 20% to 35% |
| Marble Chain, blind, level 6 | 11,900 | 18,200 | 23,500 | 40% to 44% |
| Pulse Tunnel, 128 BPM, 3,000 ticks, no input after start | 6,100 | 7,700 | 9,500 | 0% |

Marble Chain's cost grows with the balls on screen, about 135 units a ball, plus `hitTest()` over every ball for each shot in flight. A player who keeps the chain short stays inside 12,500 on every level. A long chain doesn't: still mode is over budget from level 4 up, and blind play on level 6 puts about 8% of ticks over 17,500, so the drop to 25 ticks a second doesn't cover it.

## The language

Carts are written in a subset of JavaScript compiled by `pbgc`. The full reference is `../podbox/arcade/manual/reference-language.md`; `../podbox/arcade/sdk/README.md` has the short version. What trips people up:

- **Numbers.** An integer literal (`2`) is a 32-bit integer. A literal with a point (`2.0`, `0.5`) is a fraction: 16.16 fixed point, -32768 to just under 32768, steps of 1/65536. Anything mixed with a fraction is a fraction.
- **Integers divide to integers**, truncating toward zero: `7 / 2` is 3. Write `7 / 2.0`. `Math.sqrt(2)` is 1.
- **Fractions wrap past 32767**, silently, and so does an integer above 32767 mixed with a fraction. Keep scores, frame counts and milliseconds as integers and only do fraction maths on small values or differences. Pulse Tunnel's `gt` is integer ms: `(arr[i] - gt) / bm` is safe because the difference is a few seconds, `gt * 1.0` would wrap after 32.7 s.
- **Write `0.0`, `1.0` when you mean a fraction.** `speed / 4` with an integer `speed` is a whole number. Existing code always writes the point.
- A fraction used as an index or as a position or count for the API is rounded down.
- `==` is `===`. `true` and `false` are 1 and 0. `undefined` is `null`.
- **Top level holds only declarations**: `var`, `function`, and `const` with a value known at compile time. Code that runs once goes in `init()`. Globals needing code (`new Uint8Array(n)`, literals) are set before `init()`: other files alphabetically, then `main.js`.
- **No `let` or `const` inside functions**, no arrow functions, no template strings, no `for...of`, no closures over locals, no classes, no `.map`/`.forEach`/`.filter`, no `try`. Use `var`, `for` loops and globals.
- **Global names can't clash with the API**: a function, constant group, system or namespace. `t`, `time`, `map`, `print`, `score`, `grid`, `path`, `sheet`, `data`, `store`, `frame`, `rate` and `TRACK` are taken. That's why Marble Chain uses `ROUTE`, `points` and `lvl`. Locals and parameters may reuse API names.
- **Records can't have fields named like array or string methods** (`push`, `sort` and so on).
- **Arrays**: reading past the end gives `null`. Writing past the end of a plain array stops the cart. Writing past the end of a typed array (`Int32Array`, `Uint8Array`, `FixArray`) is silently ignored. `Uint8Array` wraps values to 0..255. `Int32Array` truncates fractions; use `FixArray` for fractional positions.
- `copy(dst, di, src, si, n)` and `fill(a, v)` need arrays of one kind.
- Strings are bytes. `print("A" + x)` costs nothing extra; storing built strings each tick does.
- Every other `.js` file is a namespace named after the file: `chain.step()`, `chain.n`, `chain.left = 0`. Inside its own file its names are bare. **A namespace can call `main.js`'s functions and read its globals by their bare names.** Both carts rely on this: `chain.js` calls `popped()`, `missed()` and `gotPower()` from `main.js`; `foes.js` calls `hurt()`, `killed()`, `burst()` and reads `beatMs`, `anchor`, `bmF`; `hud.js` reads `gt`, `points` and the rest.
- Functions the cart never calls are dropped from the build.
- Angles are in turns (1.0 is a full circle). `sin` is upside down so it follows screen y.
- `rgb(0xRRGGBB)` and `deg()` only take numbers known at compile time.
- `cart.json`'s `id` is never edited by hand. Saves and scores are keyed on it.

## Marble Chain

`main.js` owns the scene (`TITLE`, `PLAY`, `WON`, `LOST`), the level, score, streak and the chain's drive (relief after a pop, slow, rewind, rush while the front is short). Each `PLAY` tick runs, in order: optional `chain.rewind()`, `chain.step(speed * k)`, `gun.update()` (which may call `chain.insert()`), the danger beep, then the win and loss checks. `title.js` borrows the chain's track arrays for the demo behind the menu via `chain.setup()`. `levels.js` holds plain parallel lists (`ROUTE`, `BALLS`, `COLOURS`, `SPEED`, `POWER`, `LABEL`): a new level is one more entry in each list plus a bump of `COUNT`.

Saved numbers: `dget(0)` is levels unlocked, `dget(1..6)` the best score per level. Scores are capped at 30,000.

### The chain engine (`chain.js`)

Read the header comment of `chain.js` and the "How the chain works" section of `docs/marbles.md` before touching it.

- The track is `PX`, `PY`: one integer point a pixel, `L` long (563, 556 and 736 for the three tracks; `MAXL` is 800). A ball is a colour and a distance `s` along it.
- All balls live in one list sorted by `s`, index 0 at the back (tunnel), `n - 1` at the front (hole). Parallel arrays: `col`, `s`, `st`, `tm`, `gap`, `pw`, `ax`, `ay`. `openSlot(k)` and `closeSlots(a, b)` shift every one of them. **Any new per-ball field must be added to both.**
- States: `ROLL` (0) normal; `ARRIVING` (1) a shot ball sliding from where it hit (`ax`, `ay`) into place over `ARRIVE` ticks; `POPPING` (2) a matched ball shrinking for `POP` ticks, then removed; `SETTLED` (3) exists only inside `step()` between the timers and matching.
- `step()` applies four rules in order: push (tunnel releases and pushes ball 0), make room (a ball closer than `D` to the one behind is pushed up to `OPEN` a tick), pull back (a run whose gap has matching colours on both sides rolls back `PULL` a tick), join (a gap that closes with the same colour on both sides calls `match(i, true)`). Then, only while `busy > 0`, timers run, finished pops are removed and settled arrivals are matched.
- `match()` pops runs of 3 or more, collects power-ups (`BOMB` handled by `blast()`, `SLOW` and `BACK` passed to `main.js` via `gotPower()`), and reports `popped(m, combo, x, y, c)`. A shot's own match that pops nothing calls `missed()`.
- `hitTest()` skips shots outside the 20x15 `near` map, then scans every ball. `insert()` puts the shot beside the ball it hit, on the side it hit.
- Nothing holds a ball index across ticks. State moves with the arrays.

Invariants that must hold at the end of every tick (`tools/marbles_stress.py` checks all of them every tick):

1. `0 <= n <= MAXB` and `left >= 0`.
2. `s` is non-decreasing (`s[i - 1] <= s[i]`; equal is allowed for a tick after an insert).
3. `counts[c]` equals the number of balls of colour `c`, and `col[i]` is in `1..colours`.
4. `st[i]` is `ROLL`, `ARRIVING` or `POPPING`, never `SETTLED`.
5. An `ARRIVING` ball has `tm` in `1..ARRIVE`, a `POPPING` ball `tm` in `1..POP`, and `busy >= tm[i]` for each of them. If `busy` runs out first, that ball is stuck for good.
6. A `POPPING` ball has `pw == 0`.
7. Where `s[i] - s[i - 1] > TOUCH`, `gap[i] == 1` (otherwise the join is never seen).
8. No ball sits behind `-D` (rewind returns those to the tunnel).
9. While `PLAY`, `front() < L - 1`.

On 2026-11-14 the stress test found no violations in 24 runs of 9,000 ticks (six levels, two seeds, smart and blind), nor in an earlier scratch run with blind shots every 8 ticks.

Fragile spots:

- `insert()` sets `busy = ARRIVE + 3`, which can lower a `busy` a pop just set. This only works because `ARRIVE + 3 == POP`. `--selftest` raises `POP` to 12 and invariant 5 fails within a few hundred ticks on every level: popping balls freeze until some other event resets `busy`.
- **Known bug:** `rewind()` returns any ball pushed behind `-D` to `left`, popping ones included. A popping ball near the tunnel during a BACK power-up has already been scored, then comes out again later as a new ball. The stress test warns `recycle` for it: 23 times in the default run, mostly in smart mode, which sets off BACK often. Confirmed by logging inside `rewind()`.

## Pulse Tunnel

- **Time**: `gt` is game time in integer ms. It follows `beat.clock()` (offset by `mOff`) while music plays and the tick clock otherwise, and never jumps. All gameplay timing runs on `gt`, so the game plays the same at 25 and 33 ticks a second.
- **Beat grid**: beat k falls at `anchor + k * beatMs`. `curBeat` is the last beat passed, `barRes` the beat residue that starts a bar, `subMs` the guns' beat (eighth notes). `beats()` advances it, calls `onBeat()` and plans every beat as it comes into view.
- **Tempo**: on a new track `beat.listen(true)` runs (6,300 units a tick) until `tryLatch()` takes a tempo with confidence 50 or more. It gives up after `LISTEN_BEATS` beats. `octave()` folds it near 500 ms and doubles anything faster than `BEAT_FAST`; the Tempo option shifts it. `nudge()` pulls the grid up to 8 ms a beat toward the tracker. `realign()` handles seeks.
- **Planning**: `plan(k)` decides what arrives on beat k, `tube.VIEW` (7) beats ahead: gates on bar starts, pickups, then heavies, spirals or drone formations. It skips a beat's enemies while `foes.count >= 22` to cap the cost.
- **Foes**: slot arrays (`MAX` 40) with an arrival time `arr` and angle. Depth in beats is `(arr - gt) / bm`. `arrive()` resolves gates, pickups and hits at depth 0. Heavies fire one spark.
- **Shots**: up to 8 volleys of 1 to 3 shots. Collision is a depth window then angle.
- **Tube**: depth d draws at scale `1 / (1 + d * K)`. Palette entries 16 to 28 are rebuilt from the album's most vivid colour, one entry a tick, because `color.toned` costs about 950 units.
- `cart.json` has `"music": "control"` (it adjusts volume on the title) and `"suspend": false` (a run against the music can't be resumed).

## Assets

Marble Chain's art and tracks are generated, not drawn: `python3 tools/marbles_assets.py` rewrites `marbles/data/path*.json`, `marbles/images/bg*.png`, `marbles/sheet.png` and `marbles/logo.png`. Change the script, never the PNGs. Re-running it reproduces the committed pixels and track data exactly, but Pillow may encode the PNGs to different bytes, so revert untouched images rather than committing byte-only changes.

- All art uses the Arcade's standard sixteen colours (the `PAL` list in the scripts) as indexed PNGs. Colour 0 is transparent.
- Sprite sheet: balls 1 to 6, popping balls 17 to 22, power-up marks 25 to 27, the gun at 32 angles as 2x2 blocks starting at sprite 64 + (b / 8) * 32 + (b % 8) * 2.
- Track JSON: `x`, `y` (one point a pixel) and `near` (300 flags, 20x15 squares of 8 px within 8 px of the track).
- `tools/pulsetunnel_logo.py` draws Pulse Tunnel's 44x44 logo.
- Sounds are sfxr settings in `sounds/*.json`, edited in the IDE.

## Code style

Match what's there:

- 4-space indent, semicolons, double quotes, `var` only.
- Every file opens with a comment saying what it is and how it works. Every function has a one-line comment above it (the IDE shows it as a hint).
- Section dividers: `// ---- name ----` padded with dashes to about column 82.
- Top-level `const` in UPPER_CASE with a trailing comment giving the unit: pixels a tick, ticks, turns, ms.
- Fixed-size typed arrays allocated at the top level. No allocation in `update()` or `draw()`.
- Short local names in hot code (`n`, `s`, `st`, `tm`), camelCase functions.
- British spelling in identifiers and on-screen text: `colour`, `centre`.
- Comments explain why, in plain short sentences.

Writing (docs, comments, commit messages): English, short direct sentences, natural contractions, no em dashes, no Oxford commas.

## Adding a new game

1. From the repo root: `node ../podbox/arcade/sdk/pbgc.js new <folder> "Game Name"`. This makes `cart.json` with a fresh `id` and a `main.js` with `init()`, `update()` and `draw()`. To start from an existing game use `pbgc.js copy <from> <folder> "Name"` so it gets its own id.
2. Fill in `cart.json`: `name`, `author` (Cyberdelia), `version`, `rate`, `help`, and any `boards`, `options` and `achievements`.
3. Split the code into namespaces by concern, as the other carts do. Keep the hot loops in typed arrays.
4. Put generated art in a script under `tools/<cart>_*.py` using the standard palette.
5. Add the folder name to the `cart` matrix in `.github/workflows/build.yml`. `build.sh` picks it up by itself; CI doesn't.
6. Add a row to the table in `README.md` and write `docs/<cart>.md` (controls, rules, how it works, performance, files).
7. Build, then measure with `pbgvm --units` against the 12,500 budget before calling it done.

## Known gaps

- The stress test doesn't run in CI. CI has no `pbgvm`; it would need the PodBox repo cloned and `host/build.sh` run.
- No perf regression gate: the stress test reports units but doesn't fail on them. Compare against the baseline above by hand.
- Pulse Tunnel has no invariant checks, only `AUTOPILOT`.
- The SDK isn't pinned: local builds use whatever `../podbox` is checked out, CI uses the builder action's `@latest`.
